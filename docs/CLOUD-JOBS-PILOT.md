# Cloud jobs: PR-only pilot

Proposed 2026-10-30, following the CTO's requirements. This narrows the first delivery from [the broader cloud-copy plan](CLOUD-IMPLEMENTATION-PLAN.md). No provisioning, paid runs or deployment is authorized by this note; the CTO supplies a cost cap before launch.

## Outcome and interface

Offload one existing Quizgecko cleanup/test loop, using its already-working harness/model. Start with one concurrent job and a fresh cloud sandbox per job. Success produces a PR for Codex autoreview and human merge. The Mac remains the interface for coordination, visual work, browser sessions and Apple tooling.

In New task, select **Cloud job**, the saved **Quizgecko tests** environment, a GitHub branch and a runtime budget. Show the resolved commit before Send. The task appears in FalconDeck's normal list with preparation progress, native agent output, approvals, cancellation, tests, usage and a PR link. **Cloud job uses pushed source**, explicitly labeled; it does not upload local edits or trust the Mac's stale checkout. Finished jobs are read-only; retry creates a linked job against an explicit revision.

## Smallest architecture

Use one operator-configured, always-on FalconDeck runner, separate from the Mac and production workloads. Reuse non-production capacity if available; account for its cost otherwise. It allocates a sandbox, starts a worker daemon and the existing native harness there, and relays task operations/events to FalconDeck. Remote provisioning, pairing and client transport are existing building blocks; per-job allocation, routing and teardown are new work. The blind relay stays transport-only.

Start with **Vercel**, qualify the real test stack, and keep Modal's VM runtime as a fallback rather than implementing two adapters. Both document Docker support. Vercel custom images require a prepared `linux/amd64` image in VCR; `ENTRYPOINT`/`CMD` are not executed, so startup must be explicit. [Vercel Docker support](https://vercel.com/changelog/run-docker-containers-inside-vercel-sandbox), [images](https://vercel.com/docs/sandbox/concepts/images), [Modal VM runtime](https://modal.com/docs/guide/sandboxes#runtimes).

## The five requirements

1. **Prepared environment.** Pin PHP, Composer, Node, pnpm and the chosen harness. Adapt the existing test Docker/Compose setup: each sandbox owns its Postgres, Redis, Meilisearch, test data, network and volumes. Prepare dependency caches from trusted source keyed by lockfiles/tool versions; never share a writable database, cache or the runner's Docker socket between jobs. Dependency changes may still need installation. Bake no credentials into images; verify package access, proxy certificates and a representative test before publishing the environment.
2. **Restricted access.** Keep compute credentials on the runner. Give the worker only task-scoped model/repository access and test configuration; omit production secrets, Doppler `prd`/`ops`, SSH keys, private network access and privileged FalconDeck connectors. Enforce an outbound allowlist and scoped worker RPC. Prefer a trusted publisher outside the worker to validate output and create the job branch/PR. Repository tokens alone do not restrict writes to main: enforce protected branches, required review and no bypass. [GitHub token scoping](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app), [branch protection](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches), [network policy](https://vercel.com/docs/sandbox/concepts/firewall).
3. **Existing gate.** Require tests and Codex autoreview from a trusted review runner/configuration, then human merge. Sandbox output and PR workflows must not obtain deployment credentials or trigger deployment. The worker cannot self-certify a passing review or merge its own PR.
4. **Enforced limits and cleanup.** Set fixed CPU/RAM/disk, a provider-side runtime deadline, one active job, per-job model allowance and a weekly pilot cap. Stop admission before the cap. An independent watchdog handles cancellation, expiry and orphan cleanup after runner restart. Enforce model spend through a metered/revocable job credential or broker; a prompt instruction or post-run usage display is not a hard cap. If the chosen harness/subscription cannot support that boundary, qualify a supported auth mode before the pilot. Budget image builds, runner, storage and model calls as well as compute. Teardown removes task compute and private volumes; explicitly disable/delete unwanted provider snapshots too.
5. **Results in FalconDeck.** Preserve source SHA, image digest, test report, diff, PR reference and native harness session files on durable runner/artifact storage before normal teardown. Operational job records are not a conversation database. Keep final detail/report access after worker deletion; qualify native history reading rather than promising it from a task title alone. On hard timeout or save failure, terminate within budget and clearly mark any missing/partial result. Never silently replay a job with an uncertain outcome.

## Delivery and acceptance

First prove one prepared-stack job through an enrolled remote worker, with an explicit test budget. Close/restart FalconDeck on the Mac mid-run, reconnect and observe completion. Verify its database is private and production access is denied. Then add only the provider lifecycle adapter, durable remote job ownership/result export and the Cloud job destination. Keep Codex on app-server, Claude on CLI, and any ACP harness on its qualified path; this is an execution destination, not a new agent framework.

Start the week-long pilot only after timeout/cancel/orphan cleanup, Mac restart, durable results, restricted publishing and the review gate pass. Measure startup latency, all-in spend per merged PR, gate pass rate, useful PR rate, peak resources and unexpected termination. No speed, cost or delivery estimate is established without that first run.

Defer dirty-source upload, exact local-session migration, worker sleep/resume, interactive follow-ups after teardown, local change import, multiple providers and public self-service onboarding. Those remain later cloud-copy work.

Meanwhile, limit concurrent heavy test stacks, share safe package caches, and separate deployment execution from the Mac. Verify archive cleanup before relying on it: the inspected `archive_thread` path only marks archival. Any cleanup must preserve uncommitted/untracked work first; retaining a Git branch preserves only committed changes.
