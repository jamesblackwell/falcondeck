# Cloud execution precedents for FalconDeck

Research date: **2026-10-06**. Prepared for James’s delegated research request. This is a UX proposal, not an implemented FalconDeck capability. All linked documentation and repository metadata were accessed on that date; publication/update dates are given where available.

## Conclusion

Give **Cloud copy** a thread-owned workspace, reusable project setup, and an explicitly available controller that can wake its worker. These are compatible choices: a durable thread need not own a continuously running VM, and a reusable environment need not share mutable files between threads. Keep an existing persistent server as a separate advanced execution destination.

The best precedents divide into three interactions: **delegate a repository task**, **attach to an existing remote session**, and **copy local work into another execution environment**. Most hosted products implement the first. Remote Control implements the second. Genuine dirty-state transfer is rarer; copying a native conversation is rarer still. FalconDeck should promise each separately, preserving Codex app-server / Claude CLI / ACP session ownership rather than replacing it with a hosted conversation database.

This assessment reads [CLOUD-SANDBOXES.md](CLOUD-SANDBOXES.md) and [CLOUD-EXECUTION-UX.md](CLOUD-EXECUTION-UX.md) as context, but does **not** establish a preferred sandbox vendor. BB is the closest native-harness lifecycle reference; Open-Inspect is the strongest inspected controller/recovery reference. Neither alone establishes a complete FalconDeck migration path.

## Vocabulary and comparison

A **model provider** supplies inference. A **harness** owns the agent loop, tools and native session. A **hosted controller** owns task routing, wake-up and client access. A **sandbox provider** supplies compute/filesystem primitives. A **remote-access wrapper** exposes an agent already running elsewhere. A product may combine these roles; a subscription to inference does not imply hosted execution.

“Off” below means the originating laptop may be off **after submission**, not that every downstream tool or approval is available. “Same thread” means logical continuity, not retained RAM. **D** = official documentation; **C** = inspected source; **I** = inference. Unknown retention and migration details remain unknown.

## Commercial interaction details

### Codex: distinguish current environments from legacy cloud

Current [Cloud environments](https://learn.chatgpt.com/docs/environments/cloud-environments) describe agent-assisted setup, review/save/**publish**, then new tasks from the prepared filesystem. Existing tasks keep their own saved files, including uncommitted work; republishing affects new tasks. Background repository refresh preserves prepared dependencies rather than rerunning all setup. This is a useful separation of **project recipe**, **published base**, and **thread workspace**.

[Modes](https://learn.chatgpt.com/docs/environments/modes) explicitly separate local, worktree and cloud execution: local processes, sign-ins and files do not automatically move. [Developer commands](https://learn.chatgpt.com/docs/developer-commands) expose cloud task creation and `codex apply`; applying the diff can fail on conflicts. A `/cloud` command is not evidence of exact native-session migration. GitHub connection, account/model entitlement and compute are distinct from environment secrets; current environment docs distinguish direct variables from proxy-substituted network secrets. Exact retention and current per-tool cloud approval behavior were not established.

The former `developers.openai.com/codex/cloud/environments` redirects to [Cloud Environment (Legacy)](https://learn.chatgpt.com/docs/environments/cloud-environment). Its cache timing and setup-secret rules must not be presented as current service guarantees.

### Claude: several different meanings of “remote”

[Cloud documentation](https://code.claude.com/docs/en/claude-code-on-the-web) now uses `claude --cloud`; older `--remote` naming is deprecated. Normal CLI submission clones the remote branch, so push first. Bundle mode can instead transfer Git history and tracked dirty changes when remote integration is unavailable, or when forced; untracked files require staging. This is actual source transfer, with size/exclusion rules, not a live mount. Starting from CLI does not transfer an existing terminal conversation.

[Desktop’s Open in → Cloud](https://code.claude.com/docs/en/desktop) carries a conversation **summary**, with a confirmation explaining file movement and archiving the original. Conversely cloud-to-terminal [teleport](https://code.claude.com/docs/en/claude-code-on-the-web) brings the pushed branch and full conversation history into a local copy. Neither creates bidirectional filesystem synchronization. Inactive cloud VMs can expire while waiting for approval/authentication; reopening restores history on fresh compute, not background shells/subagents. Permission mode survives reopening; complete file/process restoration should not be assumed.

[Remote Control](https://code.claude.com/docs/en/remote-control) attaches browser/phone to the original machine and native session; that machine must remain available. [Self-hosted runners](https://code.claude.com/docs/en/self-hosted-environments-reference) put runtime lifecycle under organization control; optional push-on-release is best effort, not a durable backup guarantee. Cloud requires the Anthropic account entitlement, source access via integration/token, and separate tool secrets; a Bedrock/model-provider account is not equivalent cloud execution authorization.

### Cursor and GitHub: delegate a repository outcome

[Cursor Cloud Agents](https://cursor.com/docs/cloud-agent) combine repository integration, environment preparation, asynchronous task views, artifacts and code review. Current naming supersedes Background Agents. Do not infer local dirty upload from the desktop entry point. [Self-hosted runtimes](https://cursor.com/docs/cloud-agent/self-hosted/choose-runtime) distinguish personal machines from organization pools: the agent loop stays in Cursor cloud while tools run on supplied hardware. A laptop worker still needs the laptop; an independent VM/pool does not. Account entitlement, source integration, worker/service credentials and runtime secrets remain separate. Exact retention and tool-level approval guarantees were not verified.

GitHub now documents [Copilot cloud agent](https://docs.github.com/en/copilot/concepts/copilot-surfaces/copilot-on-github), previously coding agent. Its [research/plan/iterate flow](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/research-plan-iterate) supports refinement before producing a PR, with bounded task execution rather than an indefinitely owned server. Chat delegation supplies context; native terminal-session migration is not established. [Security rules](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations) constrain writes to a task/PR branch, require human merge/review, and gate Actions workflows by default. These are repository outcome gates, not the same interaction as native shell approvals. Source authority follows GitHub repository permissions; hosted agent/compute follows Copilot entitlement.

### Devin, Replit and Jules: make completion reviewable

[Devin handoff](https://docs.devin.ai/work-with-devin/devin-handoff) accepts context, repository/branch and uncommitted changes through its plugin; it starts a Devin session rather than importing a native Codex/Claude session. Its [session tools](https://docs.devin.ai/work-with-devin/devin-session-tools) expose shell, IDE and browser takeover alongside chat. The [first-run flow](https://docs.devin.ai/get-started/first-run) and [secrets](https://docs.devin.ai/product-guides/secrets) separate account, repository setup, handoff API authentication and runtime credentials. PRs are the review boundary; precise sleep/retention and per-tool autonomy defaults remain unverified.

Current Replit is more than one shared project machine. [Task lifecycle](https://docs.replit.com/features/agent/task-lifecycle) makes background work an isolated copy: Draft/Active/Queued/**Ready**, then review and **Apply** to the main agent. Cancellation of started work discards it; archiving a draft is different. [Follow-up tasks](https://docs.replit.com/features/agent/follow-up-tasks) distinguish continuing work from creating another task after application. This is a strong bring-back interaction. [Agent overview](https://docs.replit.com/features/agent/overview) establishes the hosted product; local native session import, exact VM sleep behavior and laptop dirty-state upload were not verified. Project/code history should not be equated with surviving processes; Replit account entitlement, repository import authorization and project secrets are separate concerns.

[Jules getting started](https://jules.google/docs/) makes repository/branch selection and plan approval explicit. [Environment setup](https://jules.google/docs/environment/) provides a reusable prepared snapshot for task machines; [code review](https://jules.google/docs/code/) exposes task output and PR creation. Google account and GitHub integration authorize hosted inference/compute and repository access respectively. Plan approval does not establish interactive approval for every command. Exact long-term history/file retention and native local-session handoff were not verified.

### Newer precedents: Kiro, Air and Kilo

[Kiro Cloud sessions](https://kiro.dev/docs/cloud-sessions/) explicitly reuse its harness across IDE/CLI/web/mobile, with cloud-owned transcript/files and pending approvals waiting for the next attached client. This is continuity **within an existing cloud session**, not local-to-cloud migration. Repository selection is fixed at creation; personal local configuration stays local unless supported sync is configured. [Web sandbox docs](https://kiro.dev/docs/web/sandbox/) describe managed sandbox setup and deletion with the session. Account subscription covers compute; connected GitHub/GitLab supplies source authorization. Exact sleep policy remains unspecified here.

JetBrains’ [Air IDE guide, updated October 5](https://www.jetbrains.com/help/air-ides/air-start-a-new-session.html), is the closest commercial composer precedent: Local / Temporary Worktree / Cloud. Cloud requires an eligible organization, enabled tasks, account and repository connection app. Only pushed commits reach it. Environment becomes an indicator after submission; available agents/models depend on organization configuration. Conversation/tool/permission UI is consistent, but this page does not prove migrating a pre-existing native local session. Retention and cloud import details remain unverified.

[Kilo Cloud Agent](https://kilo.ai/docs/code-with-ai/platforms/cloud-agent) offers repository profiles, setup/secrets, idle spindown and a saved Changes view that can be read without waking compute. Its beta retention says seven days. The user-facing description shares a user container and sometimes a worktree; [current architecture](https://kilo.ai/docs/contributing/architecture/cloud-platform) instead describes separate execution paths, owner-shared sandboxes, organization per-session sandboxes and devcontainer paths. Treat this as a documentation/version boundary, not universal isolation. Cloudflare-backed control services handle orchestration. Account/gateway or BYOK inference and compute billing are distinct; native-session migration and approval semantics remain unverified. Saved diff freshness is a useful UX pattern regardless of backend.

## Five inspected source references: study, not adopt

These are actual lifecycle/runtime/source-transfer reads, not README-only endorsements. Links pin the revision inspected; none of these runtimes was provisioned or tested.

### 1. BB: native worker plus durable filesystem checkpoint

Local `../bb` was inspected at **5d31d8c32d85d7bde75d211b8295836b33fc2a26** (October 5), one day behind the remote head at research time. MIT. [Provider orchestration](https://github.com/get-bb/bb/blob/5d31d8c32d85d7bde75d211b8295836b33fc2a26/apps/server/src/services/machines/provider-orchestration.ts) distinguishes thread-owned and standalone machines and flushes/stops the host daemon before suspension. [Modal backend](https://github.com/get-bb/bb/blob/5d31d8c32d85d7bde75d211b8295836b33fc2a26/plugins/environment-modal-sandbox/providers/modal/backend.ts) snapshots files before terminating, records the checkpoint, then starts replacement compute from that snapshot. This is filesystem restoration, not live-process suspension.

[Project initialization](https://github.com/get-bb/bb/blob/5d31d8c32d85d7bde75d211b8295836b33fc2a26/apps/host-daemon/src/command-handlers/project.ts) performs Git clone, not automatic dirty-local upload. Machine/provider setup and native agent authentication are separate. Native session files can travel with the filesystem, but exact migration from an existing local session was not demonstrated. Central server placement determines laptop-off wake-up; a worker alone cannot replace its controller. The reviewed backend’s finite lifetime makes checkpoint-before-expiry important. Study native ownership and checkpoint ordering; do not copy a lifecycle without expiry protection.

### 2. Open-Inspect: recovery belongs to an available controller

ColeMurray/background-agents, **2e626cce896219300a54660a139e39f7a7bb4e92** (October 6), MIT. [Lifecycle manager](https://github.com/ColeMurray/background-agents/blob/2e626cce896219300a54660a139e39f7a7bb4e92/packages/control-plane/src/sandbox/lifecycle/manager.ts) handles spawn/restore/reconnect, readiness and rotating worker authentication. [Shutdown coordination](https://github.com/ColeMurray/background-agents/blob/2e626cce896219300a54660a139e39f7a7bb4e92/packages/control-plane/src/session/sandbox-shutdown.ts) records durable shutdown progress and protects saved-state recovery; restore failure is not silently replaced with a fresh checkout. [Repository sync](https://github.com/ColeMurray/background-agents/blob/2e626cce896219300a54660a139e39f7a7bb4e92/packages/sandbox-runtime/src/sandbox_runtime/repository_sync.py) clones a branch using brokered credentials.

The deployed Cloudflare controller can wake provider workers without a laptop; its cloud harness/session model is not evidence of importing FalconDeck native sessions. Web/integration tasks lead to Git review; native approval equivalence was not verified. Its documented single-tenant trust assumptions and shared source integration deserve attention before multi-user reuse. Study stale-worker detection, durable recovery status and credential separation; do not adopt its conversation ownership wholesale.

### 3. OpenHands: API lifecycle is not one uniform product contract

OpenHands GUI **81e83760a196ba6374ad2c3d38d577262c79ca2d** and software-agent-sdk **6f8c38d00e0468ac138447be905f07a8a0cd7af8** (October 6), MIT. The SDK’s [CloudWorkspace](https://github.com/OpenHands/software-agent-sdk/blob/6f8c38d00e0468ac138447be905f07a8a0cd7af8/openhands-workspace/openhands/workspace/cloud/workspace.py) creates or reconnects a sandbox and obtains its agent-server URL/key. Default cleanup can delete it; `pause()` is explicitly unimplemented for that cloud API. The [remote API implementation](https://github.com/OpenHands/software-agent-sdk/blob/6f8c38d00e0468ac138447be905f07a8a0cd7af8/openhands-workspace/openhands/workspace/remote_api/workspace.py) has different pause/resume semantics. Do not combine them into a fictional universal sleep guarantee.

[Remote workspace transport](https://github.com/OpenHands/software-agent-sdk/blob/6f8c38d00e0468ac138447be905f07a8a0cd7af8/openhands-sdk/openhands/sdk/workspace/remote/remote_workspace_mixin.py) uploads/downloads files over HTTP; this does not automatically transfer a dirty checkout. Source credentials, model access and runtime-session keys have different roles. Hosted service or independently deployed controller permits laptop-off operation; self-hosting assigns availability to the operator. UI task/PR history is distinct from compute retention; full hosted approvals/retention were not audited. Study the attachable runtime boundary, not an assumed native-session conversion.

### 4. Cline: an actual controller, without automatic sandbox provision

Cline **dec80dadfa4fcb5ec6978aa7055406709dddd43d** (October 6), Apache-2.0. [Remote runtime host](https://github.com/cline/cline/blob/dec80dadfa4fcb5ec6978aa7055406709dddd43d/sdk/packages/core/src/hub/runtime-host/remote-runtime-host.ts) connects an authenticated client to a Hub with working directory and capability declarations; it does not upload a repository or create a cloud VM. [Session handlers](https://github.com/cline/cline/blob/dec80dadfa4fcb5ec6978aa7055406709dddd43d/sdk/packages/core/src/hub/server/handlers/session-handlers.ts) start sessions with server-owned permissions. [Hub/spoke architecture](https://github.com/cline/cline/blob/dec80dadfa4fcb5ec6978aa7055406709dddd43d/docs/sdk/architecture/hub-spoke.mdx) separates coordination, session records/approvals and agent processes.

This is a meaningful local-first controller reference, but user-hosted remote execution depends on where spokes and tool capabilities run. A remote Hub using a local client’s shell still depends on that client. Cline-native continuity is not Codex/Claude migration. Model credentials, Hub access, repository access and server hosting remain operator concerns; no managed import/PR or sleep policy was established for this SDK path.

### 5. OpenCode: remote attachment is not hosted execution

OpenCode **f03046d9f558bc54a090363fea48441b05f522bf** (October 6), MIT. [Serve command](https://github.com/anomalyco/opencode/blob/f03046d9f558bc54a090363fea48441b05f522bf/packages/opencode/src/cli/cmd/serve.ts) starts a headless HTTP server; [session code](https://github.com/anomalyco/opencode/blob/f03046d9f558bc54a090363fea48441b05f522bf/packages/opencode/src/session/session.ts) stores project/directory-linked native sessions and supports forks. Neither inspected path provisions a worker or copies local files to a remote server. The operator supplies checkout, runtime uptime, endpoint authentication and inference credentials; Git review/import remains their workflow. Native permissions operate on that host. Study attach/reconnect; do not equate model gateway Zen with hosted compute.

## Recommended FalconDeck interactions

1. **Keep the composer choice small.** Project folder / Isolated copy / Cloud copy chooses where files and tools live. Selecting Cloud copy reveals repository source, native harness, setup preset and execution host. Reusable setup is project-scoped; mutable checkout/session state is thread-scoped. Offer an existing persistent server separately when users need configured infrastructure.
2. **Show what will actually move.** Default handoff should offer “Copy current working state” with base commit, dirty-file count and excluded/untracked files, plus “Use remote branch” with resolved commit. Label an offline laptop snapshot “Captured at …”; never call it current. If copying cannot happen while the source daemon is offline, explain which last saved source is available before submission.
3. **Separate conversation transfer from source transfer.** Offer “Continue native session” only after that harness’s native files, identifiers, configuration and resume behavior are verified. Otherwise say “Start cloud thread with summary” and link the original. Do not imply `/cloud`, a plugin handoff, or the same chat layout proves native migration. Keep original sessions recoverable and prevent two active writers to one native session.
4. **Set up once, then make environment fixed and visible.** Verify compute connection, repository access, agent login and required secrets separately. Show preparation progress and a testable setup result. After creation, display the environment/version as a thread attribute; changing it should be an explicit migration/new-copy operation, not a hidden follow-up side effect.
5. **Let follow-ups address the thread, not a VM.** A sleeping thread should say “Waking workspace” and restore the same native session plus saved files. A controller must be reachable independently of the laptop for this promise. Explain “Controller offline” separately from “Worker sleeping”; an always-on coordinator can be small while workers scale to zero. This need not become another conversation source of truth.
6. **Preserve approvals across detachment.** Show Waiting for approval, keep the native request identity, and reconcile it with the resumed agent before answering. Do not auto-approve because work is remote. A stale request after worker replacement needs explicit recovery, not replay into a different process. Kiro’s attachable approvals and Air’s consistent permission UI are useful precedents.
7. **Make recovery and bringing back first-class.** Distinguish durable transcript, saved files and lost processes. Show last successful checkpoint and diff capture time without waking compute. Restore failure should offer retry or an explicitly fresh workspace, preserving the failed checkpoint. Provide Review changes → Apply to selected local destination / Create PR, with base comparison, dirty-destination conflict handling and a persistent result if application fails. Bringing code back and moving the native session back are separate actions.

### Verification boundary

Verified: current public official docs, dated repository metadata, and pinned source paths for lifecycle, source clone/upload, runtime attachment and shutdown/recovery. No authenticated UI, actual provisioning, installations, native-session migration or fault-injection was performed. Provider retention, current approval defaults where marked, Kilo’s differing documentation paths, and cross-machine native resume compatibility require targeted validation before implementation. FalconDeck’s remote-host proposal is not treated as shipped behavior. No runtime tests are needed for this document.
